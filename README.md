# Android Screenshot Tool 1.1.5

Консольная утилита для Windows и Linux, которая делает снимки экрана Android через `adb`.

## Возможности

- единый список USB- и сетевых устройств из `adb devices -l`;
- выбор устройства стрелками `↑/↓`, `Enter` или цифрами;
- выбранное устройство постоянно видно в главном меню;
- при открытии списка устройств курсор стоит на выбранном сейчас устройстве;
- последнее выбранное устройство сохраняется между запусками и автоматически восстанавливается, если доступно;
- главное меню сохраняет ранее выбранную строку, поэтому повторный снимок можно делать одним Enter;
- если устройство ещё не выбрано, команда снимка сначала открывает выбор устройства;
- PNG без перекодирования;
- JPG с качеством 99, без цветовой субдискретизации (`subsampling=0`);
- имя файла: `Модель_YYYY-MM-DD_HH-MM-SS.png|jpg`;
- снимки сохраняются в подкаталог Screenshots текущей рабочей папки;
- видео сохраняются в подкаталог Videos текущей рабочей папки;
- каталоги Screenshots и Videos исключены из Git и не попадают в публичный репозиторий;
- запись видео: MP4/H.264, yuv420p, аварийно-восстанавливаемый fragmented MP4 во время записи и faststart после штатной остановки;
- ограничение частоты захвата видео: 6, 12, 24, 30, 45 или 60 FPS;
- микрофон Android выключен по умолчанию и включается только на совместимых прошивках с доступным tinycap;
- перед снимком состояние выбранного устройства проверяется повторно;
- `offline` и `unauthorized` показываются в списке, но не выбираются как рабочие;
- при запуске исходного `.py` Pillow для JPG устанавливается автоматически, если отсутствует;
- EXE и DEB собираются как автономные бинарники с Pillow внутри.

## Требования

- `adb` заранее установлен и доступен в `PATH`;
- для запуска исходного файла: Python 3;
- для сетевого Android устройство должно быть доступно для `adb connect IP:PORT`; последнее сетевое устройство программа пытается переподключить автоматически;
- для записи видео нужен FFmpeg; программа пытается установить его автоматически там, где это возможно.

## JL22 / UniWin_M190 и stale framebuffer

На Jetinno JL22 / UniWin_M190 с Android 6 обнаружен vendor-дефект: системный `screencap` иногда продолжает возвращать старый аварийный framebuffer, хотя реальный логический экран уже другой. Ошибка повторяется одинаково по USB и сетевому ADB.

Диагностика на физическом устройстве показала:

- `adb exec-out screencap -p` → старый кадр 800×1280;
- `screencap` во временный файл + `adb pull` → тот же байт-в-байт кадр;
- SHA-256 этого известного stale-кадра: `0bafc5252f4474e58d26dfca14a07201bd5bc8b7af6a14bf0b2b025778c3e711`;
- `screenrecord` в тот же момент видит настоящий актуальный экран 1280×800.

Поэтому начиная с 1.1.5 программа работает хирургически: обычный `screencap` остаётся основным путём для всех устройств, но если получен именно известный stale SHA-256 JL22, программа на одну секунду использует `screenrecord` и извлекает первый актуальный кадр через FFmpeg.

Это не эвристика по ориентации и не глобальная замена `screencap`; рабочее поведение остальных устройств не меняется.

## Alt+F4 на Windows

На Windows консольное приложение теперь обрабатывает закрытие окна / Alt+F4 через системный `CTRL_CLOSE_EVENT`. Меню опрашивает клавиатуру без вечной блокировки, поэтому приложение может корректно выйти. Если в этот момент идёт запись видео, утилита пытается сначала штатно остановить видеопроцесс и завершить упаковку файла.

## Резервный захват снимка

Основной путь снимка не изменён:

```text
adb -s <serial> exec-out screencap -p
```

На некоторых vendor-ROM (в частности, отдельных Vivo) ADB может вернуть перед бинарным PNG служебный текст либо вообще некорректный поток. В 1.1.4 это обрабатывается без изменения поведения остальных устройств:

1. программа сначала ищет корректный PNG в обычном `exec-out` ответе;
2. если перед PNG есть короткий служебный префикс, он отбрасывается;
3. если корректного PNG нет, программа создаёт временный PNG на Android;
4. временный файл забирается через `adb pull`, то есть через другой ADB-механизм;
5. после проверки временный файл удаляется.

Резервный путь используется только после отказа обычного `exec-out`.

## Старые Android и параллельные ADB-сеансы

В 1.1.3 восстановлен простой проверенный путь `adb exec-out screencap -p`. Предыдущая попытка автоматически определять «неправильный framebuffer» по системной ориентации оказалась ненадёжной на старом vendor-ROM и была полностью убрана.

Известный редкий сбой UniWin_M190 при одновременной нагрузке от другого ADB-клиента пока не блокируется автоматически: надёжнее временно получить редкий неверный кадр, чем отвергать правильные снимки. Для этого случая нужна отдельная диагностика именно поведения старого `adbd/SurfaceFlinger`.

## Видео

Начиная с 1.1.1 запись выполняется через **scrcpy**, а не через самодельную цепочку `screenrecord → FFmpeg`. Это важно по трём причинам:

- таймстемпы кадров формируются на самом Android;
- scrcpy учитывает ориентацию дисплея и при старте фиксирует текущую ориентацию записи;
- тяжёлого перекодирования каждого кадра на компьютере во время записи больше нет.

Выбор 6 / 12 / 24 / 30 / 45 / 60 задаёт **верхний предел FPS** через `scrcpy --max-fps`. Реальная частота может быть ниже, если экран обновляется реже.

Во время записи используется временный Matroska-файл `.recording.mkv`. MKV выбран специально как более устойчивый к незавершённой записи контейнер. После штатной остановки FFmpeg быстро, без повторного кодирования видео, перепаковывает его в MP4/H.264 с `faststart` (заголовок `moov` помещается в начало файла). Это удобно для браузеров и Telegram.

При следующем запуске оставшиеся `.recording.mkv` автоматически перепаковываются в MP4. Старые `.recording.mp4`, созданные ошибочным видеодвижком 1.1.0, больше не пытаются восстанавливаться бесконечно: они переносятся в `Videos/Legacy_1.1.0/` и сохраняются как есть.

Для записи требуются **scrcpy** и **FFmpeg**. На Windows программа пытается установить их автоматически через WinGet:

- `Genymobile.scrcpy`;
- `Gyan.FFmpeg`.

На Linux программа сначала ищет установленные `scrcpy` и `ffmpeg`, затем при наличии `apt-get` пытается установить недостающие пакеты.

### Микрофон Android

По умолчанию звук выключен.

- Android 11+ — программа использует штатный `scrcpy --audio-source=mic` и AAC;
- Android 10 и старше — scrcpy не умеет передавать звук, поэтому программа дополнительно пробует `tinycap`, если он присутствует в прошивке и доступен ADB-shell;
- если ни один способ не доступен, запись продолжается без звука и программа сообщает об ограничении.

## Обновление

Windows:

```bat
update.bat
```

Linux:

```bash
./update.sh
```

Обновляющий сценарий останавливается при наличии локальных незакоммиченных изменений, выполняет только fast-forward pull, проверяет синтаксис Python, версию программы и наличие ADB. update.bat запускает рабочую часть из временной копии, поэтому способен безопасно обновить сам себя. На Windows он также добавляет точный каталог проекта в Git `safe.directory`, если владелец каталога отличается от текущего пользователя.

## Сборка EXE на Windows

Запустить:

```bat
build_exe.bat
```

Сценарий сам:

1. создаёт `.venv-build-win`;
2. обновляет `pip`;
3. устанавливает Pillow и PyInstaller;
4. собирает `dist\AndroidScreenshotTool.exe`.

## Сборка DEB на Debian/Ubuntu

Запустить:

```bash
chmod +x build_deb.sh
./build_deb.sh
```

Сценарий сам устанавливает недостающие системные средства сборки через `apt-get` (с `sudo`, если он доступен), создаёт `.venv-build-linux`, загружает Pillow и PyInstaller, собирает автономный Linux-бинарник и затем `.deb` в каталоге `dist/`.

Установка готового пакета:

```bash
sudo apt install ./dist/android-screenshot-tool_1.1.5_*.deb
```

После установки запуск:

```bash
android-screenshot-tool
```

## Ограничения

- Утилита не включает Android Platform Tools внутрь EXE/DEB и не меняет настройки ADB: по условию задачи `adb` уже должен быть доступен в `PATH`.
- `build_exe.bat` нужно запускать именно в Windows: PyInstaller собирает исполняемый файл для текущей ОС.
- `build_deb.sh` собирает пакет для архитектуры Linux-машины, на которой он запущен.

## Готовые выпуски

Теги вида `v*` запускают GitHub Actions, который собирает Windows EXE, Debian DEB, чистый ZIP исходников через `git archive`, файл `SHA256SUMS.txt` и публикует их в GitHub Releases.

`Screenshots/`, `Videos/`, кэши Python, виртуальные окружения и результаты локальной сборки в архив исходников не попадают.
